# How we work

*A note on method — written from the inside, after a long session on Vinculum.*

These projects (MermaidKit, then Vinculum) are built the same way, and the method
matters more than any individual commit. This is an attempt to write it down
honestly, including the parts where it caught me being wrong.

A caveat up front: the concrete examples here are from Vinculum, because that's
the work in front of me. The practices aren't Vinculum's — the layout/render
split and the package-traits trick both arrived here *from* MermaidKit. What
follows is the shared method.

---

## 1. Proof beats assertion, and the proof has to be generated

The rule: if a document claims something, the claim should be *checkable*, and
ideally regenerated by a machine rather than typed by a human.

- **The gallery figures** are regenerated from the live engine on every push
  (`GalleryGenerator`, `CommandGalleryGenerator`, `AlgorithmGalleryGenerator`, … →
  the `gallery` branch). A wrong-looking figure means a wrong engine — this has
  caught real bugs (a mis-seated `\vec`, dropped chart coverage). Screenshots rot;
  generators don't.
- **The pdfTeX comparison** is a committed static asset, reproduced by a committed
  script (`scripts/compare-tex.sh`) — *not* by CI, because installing TeX Live on
  every run buys little for three images that change approximately never. And be
  precise about what it claims: it is a matched-**height** visual side-by-side, not
  a pixel diff, and **no tolerance is defined**. The two renders are close, not
  identical — at equal height the quadratic's aspect is 3.64 (pdfTeX) vs 2.94.
  "Judge the fidelity yourself" is doing real work in that sentence.
- **The wordmark** is `\sqrt{\mathrm{Vinculum}}`, typeset by the engine it
  advertises. That was true exactly once — when the PNG was generated — and then
  nothing re-checked it, so the front page was asserting something unverified. It
  is now a test (`WordmarkTests`): re-render, compare against the committed asset,
  go red on drift. Dogfooding isn't cute; it's a load-bearing claim, and a
  load-bearing claim deserves a check.

> This section originally read *"Every figure in the docs is regenerated from the
> live engine on each push."* A survey of the essay's own claims found that false
> for exactly the two most rhetorically loaded figures — the fidelity comparison
> and the wordmark. Rule 2 applies to prose as much as to tests: an unchecked
> claim is a rumour, and the ones you most want to be true are the ones to check
> first.

The general form: **make the marketing a test.**

## 2. A test that has never failed is a rumor

This is the discipline I'd most want a newcomer to steal, because it saved this
session twice.

When I fix a bug, I revert the fix and re-run the test. If it still passes, the
test is decoration. Both parser fixes went through this and failed correctly on
`main` before I trusted them.

Then I wrote a Linux golden harness — a signature of where ink lands in a render —
and ran the same check: I zeroed one equation's golden to simulate a blank render.
**The test passed.** My signature averaged darkness across each cell, which
diluted thin glyph strokes to nearly zero, so every cell quantized to 0 or 1 and
tampering moved nothing. I had written a test that could never fail, for an issue
whose entire complaint was "a broken render passes CI silently." The tamper check
is the only reason it didn't ship.

Corollary: **the bug you're most likely to ship is in the thing that's supposed to
catch bugs.** Test the tester.

## 3. Measure; then believe the measurement over your own docs

Asked "do we understand every microsecond?", the honest answer was no — so we
built a phase profiler instead of arguing. It disagreed with our own README:

- The claimed "cold render ≈ 0.3 ms (parse → layout → rasterize)" was a *debug*
  number, and mislabeled: `NSImage(size:flipped:)` is **lazy**, so `rendered()`
  never rasterizes. The pixels are drawn on first paint, ~0.23 ms later. macOS
  defers; iOS is eager. Same work, different moment.
- ~77% of a cold render is CoreText measuring and drawing glyphs. Our own parse +
  geometry is under a fifth. The interesting number wasn't the one we'd been
  quoting.

We fixed the README rather than the measurement. Documentation that flatters the
code is a liability; the profiler is now committed so the numbers can be re-derived
rather than re-remembered.

## 4. Degrade, never vanish

The strongest invariant in the codebase: unsupported input becomes a *visible*
source card, never a half-render and never silence.

`a_b_c` is TeX's "Double subscript" error. We were silently dropping the earlier
atom and rendering `a_c` — content deleted, no diagnostic. The fix wasn't to guess
the user's intent (`a_{bc}`) but to surface it. Guessing silently is just a
politer way of losing data.

The same instinct drives the reconstruction detail: we brace only *composite*
pieces, so `a_b_c` degrades to the literal string `a_b_c` and the diagnostic can
actually point at it. A fallback you can't locate is half a fallback.

## 5. Generation is cheap; verification is the product

The 47 issues on this repo came from eleven domain experts (Swift, concurrency,
AppKit, UIKit, SwiftUI, Cairo/FreeType, OpenType, LaTeX, Knuth/Appendix G,
architecture, CI) fanned out in parallel — then **every candidate was handed to an
adversarial validator that re-read the actual code before anything was filed.**

Five of fifty-two died there, and the rejections are the most interesting output:

- A "SwiftUI dark-mode bug" — refuted by finding `.alwaysTemplate` baked at a
  specific line, which SwiftUI honors.
- A "Rule 18 script inversion" — refuted against TeX82's `make_op §749`: the code
  was a *faithful* port, and the reviewer's premise about vanilla TeX was wrong.

A panel of experts will confidently hand you plausible fiction. The value isn't the
finding; it's the finding that survived someone trying to kill it. Filing all 52
would have been worse than filing none — it would have burned trust in the list.

## 6. Small, reversible, boring increments

Asked for "the most sane way with the least complications," the answer was: one
issue per branch, one small PR, CI-gated, independently revertible. No mega-branch.
Anything with a judgment call in it gets its own PR so it can't muddy a clean merge.
Anything that changes pixels waits until the safety nets exist.

That ordering is deliberate: **safety nets, then correctness, then structure, then
features.** We pinned the Linux CI graph and built the golden harness *before*
touching the high-priority font bug, so its pixel diff would land against a net
instead of a shrug.

It also means knowing when to stop. Several times the honest move was "these
remaining items each have a wrinkle — here's the boundary" rather than bulldozing
through and calling it done.

## 7. The human half

The working relationship has a shape, and it's worth naming.

- **Terse, high-trust directives.** "yep." "keep going." "whatever makes the most
  sense." Judgment is delegated, not micromanaged — which only works because the
  next item is also true.
- **Hand-waving is not accepted.** *"I do not believe in flakiness, only
  not-yet-understood smells."* That one sentence turned a shrug about a "flaky"
  Linux build into a root cause (QEMU faulting `swiftc` under amd64 emulation) and
  a real fix (build native arm64). "Flaky" is almost always a synonym for "I
  stopped looking."
- **The bar is raised with questions, not specs.** "Do we understand every
  microsecond?" produced a profiler, a report, and three corrected claims. "Can we
  render the logo with Vinculum too? :)" produced the dogfooded wordmark. Good
  questions are cheaper than requirements documents and produce better work.
- **Corrections are fast and cheap.** "no, the Linux path is using
  PureSwift/Silica." "sorry I mean 49." No ceremony, no blame — just a course
  change. Cheap correction is what makes high-trust delegation safe.
- **Review is plural.** CodeRabbit, Copilot and codex all review; their feedback
  gets forwarded rather than filtered. codex caught that my ink signature measured
  only the red channel — so `\color{red}` glyphs (R=255) read as *blank*, and the
  test was structurally blind to part of the render it guarded. That was a real
  hole found by a bot, in code I'd already convinced myself was rigorous.

The pattern: **the human supplies taste, skepticism, and direction; the machine
supplies throughput and stamina; neither is trusted to self-certify.**

## 8. Architecture that makes the method possible

None of the above works without the split: layout is platform-free (Foundation
only) and rendering is injected through seams. That's why 220 tests run headless in
a Linux container, why geometry is asserted as exact numbers instead of eyeballed,
and why a Linux raster backend could be added without touching typesetting code.

The method and the architecture are the same decision viewed from two angles. You
can only test what you can isolate.

---

## The short version

1. Generate your proof; don't type it.
2. Break the test on purpose, or you don't have one.
3. Measure, and believe the measurement over the docs.
4. Degrade loudly; never vanish.
5. Verify what you generate — especially when it's confident.
6. Small, reversible, in the boring order: nets → correctness → structure → features.
7. Say "I don't know yet" instead of "flaky."
